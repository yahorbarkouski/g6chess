# ADR 0005: KISS Context With Candidate Practicality

Date: 2026-04-30
Status: Accepted

## Context

The context engine must feed one explanation string for one move. ADR 0004
introduced evidence packets and coach context, but the initial shape included
too many prompt-like fields and did not strongly enough represent whether
engine-recommended moves are realistic for the player to find.

The product should not blindly recommend Stockfish top moves. Some engine moves
are too hard for the player level or time situation and should be explained with
a caveat, replaced by a practical alternative, or used only as a benchmark.

## Decision

The context engine will still produce two artifacts:

1. **Evidence Packet**: complete internal truth for verification and tests.
2. **LLM Context**: compact deterministic projection used for production
   generation and future training inputs.

The LLM context is not generated by another LLM. It is built by context-engine
code from verified evidence.

Per-request LLM context should stay KISS. It should include chess facts and
explanation decisions, not generic prompt fields such as tone, audience prose,
or do-not-include lists.

Every important candidate move must carry:

- objective engine score
- score loss versus best
- short relevant line when useful
- human play probability or `unknown`
- time-adjusted findability or `unknown`
- practicality category
- recommendation policy

The context engine distinguishes objective move quality from practical
recommendability.

## Consequences

The final explanation can say:

```text
The engine move was best, but it was hard to find at this level.
```

instead of overclaiming:

```text
You should obviously have played the engine move.
```

This improves coaching quality while keeping the API focused on one explanation
string.

## Alternatives Considered

### Use Stockfish ranking only

Rejected. It produces engine-centric explanations and over-recommends obscure
moves.

### Let the LLM decide practicality

Rejected. The LLM would infer from incomplete evidence and may invent claims
about what players can find.

### Put prompt instructions into context

Rejected. Static behavior belongs in the prompt or API contract. The context
should carry per-position facts and decisions.

## Validation

This decision is working if:

- hard engine moves are caveated
- close practical alternatives are recognized
- Maia/frequency evidence affects wording but not objective quality
- explanations stop implying that every best move was obvious
- production and training use the same LLM context shape
- verifier checks can trace explanation claims back to the evidence packet
