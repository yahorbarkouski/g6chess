# Context Engine

This document defines the context engine for the focused single-move explanation
API.

The public product remains:

```text
explain_move(game_context, played_move, player_level) -> explanation_string
```

The context engine turns the requested move into the factual and practical
context needed for one coach-quality explanation string.

## Core Principle

The LLM should not decide chess truth or practical move relevance.

The context engine should decide:

- what happened
- how good or bad the move was
- which alternatives matter
- how findable those alternatives are for this player
- what the safest explanation point is

The LLM should only phrase that context clearly.

## Why This Matters

The objectively best move is not always the move we should recommend without a
caveat.

Some Stockfish moves are:

- obvious and should be recommended directly
- strong but hard to find at the player's level
- engine-best but barely better than a simpler practical move
- only moves, even if hard
- tactically correct but unrealistic in blitz or low time

If the context does not represent this, the explanation will sound like a bad
coach:

```text
You should have played Qh5+.
```

when the better coaching explanation may be:

```text
The engine's best move was Qh5+, but that is a hard forcing idea to find in
blitz. The practical lesson is that before pushing g4, you needed to check
forcing moves first; Qh5+ works because it makes Black respond immediately.
```

This distinction is central to the product.

## Context Engine Output

The context engine should produce two artifacts.

### Evidence Packet

The evidence packet is the complete internal truth record.

It is used for:

- deterministic verification
- tests
- debugging
- evals
- future training data generation

It can contain full engine details, raw values, all candidate moves, and
diagnostic metadata.

### LLM Context

The LLM context is a compact, deterministic projection of the evidence packet.

It is not generated by another LLM. It is built by the context engine from
verified evidence and fixed heuristics.

It is used for:

- production explanation generation
- prompt evals
- future fine-tuning inputs

The production and training inputs should stay aligned. If production uses the
LLM context, training should train the model on the same kind of context.

## KISS Boundary

The LLM context should contain chess facts and explanation-relevant decisions.
It should not contain generic prompt instructions.

Keep out of per-request context:

- tone
- audience prose
- do-not-include lists
- long style rules
- generic output formatting instructions

Those belong in the static prompt or API contract.

Keep in per-request context:

- player level
- time situation
- played move quality
- candidate move strength
- candidate move findability
- main explanation point
- allowed chess claims
- forbidden chess claims when needed for safety

## Inputs

Required in some accepted form:

- game context, such as PGN or FEN before the move
- played move, preferably UCI or another unambiguous move identifier
- player color
- player level or rating

Optional but useful:

- time control
- clock before the move
- increment
- move number or ply
- recent move history
- opponent rating
- game result

The context engine should reject ambiguous input rather than explain the wrong
move.

## Required Evidence Sources

### Deterministic Board State

Required.

This includes:

- valid FEN before the move
- legal move list
- played move legality
- FEN after the move
- UCI and SAN notation
- side to move
- player color
- castling and en passant rights

If reconstruction fails, no explanation should be generated.

### Stockfish

Required for production-quality explanations.

Use Stockfish for:

- best candidate moves before the played move
- forced analysis of the played move
- after-move best reply or opportunity
- centipawn or mate score
- WDL when available

Important: Stockfish supplies objective strength. It does not tell us what is
reasonable for the player to find.

### Maia / Human-Likeness Model

Optional but highly valuable.

Use Maia-2 or a similar human-likeness model for:

- played move probability at player level
- candidate move probability at player level
- candidate move probability at stronger levels
- skill-gap signals
- common-trap or hidden-idea interpretation

Maia-style evidence is about likelihood, not quality. A high-probability move
can still be bad. A low-probability move can still be best.

Maia-2 is especially useful because its public implementation supports
position-wise inference conditioned on active-player and opponent Elo, and has
separate blitz/rapid model types. Use time control to select the closest model
when available.

### Empirical Human Move Frequencies

Optional later, but important for improving practical recommendations.

From clean game data, we can compute:

- how often each candidate is played in similar positions
- frequency by rating band
- frequency by time control
- frequency by move number or phase
- sample size and confidence

This is different from Maia:

- Maia generalizes to unseen positions.
- Empirical frequencies are concrete but sparse and biased toward common
  positions.

Use empirical data only with sample counts and confidence. Do not let sparse
frequency data override strong engine evidence.

### Syzygy Tablebases

Optional for endgames, but exact when applicable.

Use tablebases when the position has few enough pieces and tablebases are
available. They prevent endgame explanations from relying on shallow heuristic
engine scores.

Tablebase evidence should override normal engine uncertainty for exact
win/draw/loss claims.

### Concept Detectors

Optional at first.

Use rules and later classifiers for:

- hanging piece
- missed check
- fork
- pin
- skewer
- back-rank weakness
- king safety
- development
- initiative
- pawn structure
- move-order issue

Concept tags must include source and confidence. The LLM should not receive a
tag as a fact unless the context engine is willing to allow that claim.

## Candidate Move Model

Candidate moves are the heart of the context.

Every proposed move or line in context should carry both objective value and
human findability.

Candidate sources:

- Stockfish top moves
- the played move
- Stockfish forced played-move line
- Maia top human moves
- close practical alternatives
- tablebase-preserving moves in exact endgames

Illustrative candidate shape:

```json
{
  "move_uci": "d1h5",
  "move_san": "Qh5+",
  "role": "engine_best",
  "engine": {
    "rank": 1,
    "score": {"kind": "cp", "value": 62},
    "score_loss_vs_best_cp": 0,
    "wdl": {"win": 115, "draw": 760, "loss": 125},
    "pv_short_san": ["Qh5+", "Nf6", "Qxe5+"]
  },
  "human": {
    "player_level_probability": 0.03,
    "plus_400_probability": 0.18,
    "time_adjusted_findability": "hard",
    "evidence_source": "maia2_blitz"
  },
  "recommendation": {
    "policy": "mention_with_caveat",
    "reason": "objectively best, but low probability for this level and time control"
  }
}
```

This structure prevents us from blindly recommending impossible-to-find moves.

## Candidate Roles

Use explicit roles so the LLM does not confuse candidate meaning.

Suggested roles:

- `played_move`
- `engine_best`
- `close_engine_alternative`
- `practical_alternative`
- `human_common_move`
- `best_reply_after_played`
- `only_saving_move`
- `only_winning_move`
- `tablebase_exact_move`

A move can have multiple roles, but the LLM context should expose the simplest
meaning needed for explanation.

## Recommendation Policy

The context engine should decide how each candidate may be used.

Suggested policies:

- `recommend_directly`: strong and reasonably findable
- `mention_with_caveat`: best or critical but hard to find
- `use_as_practical_alternative`: not best, but close and more realistic
- `explain_as_hidden_resource`: important because it was hard to see
- `do_not_recommend`: useful for analysis but not for the explanation

Examples:

```text
Stockfish best, Maia low, score gap huge:
  mention_with_caveat or explain_as_hidden_resource

Stockfish second, Maia high, score close to best:
  use_as_practical_alternative

Only move to avoid mate, Maia low:
  mention_with_caveat, but still explain it because it is critical

Engine best is +0.03 better than a simple human move:
  do not overemphasize engine best
```

The final explanation can still mention the engine-best move, but the wording
must reflect findability.

## Findability

Findability is not the same as correctness.

The context engine should estimate findability from:

- Maia probability at player level
- Maia probability at stronger levels
- empirical frequency when available
- time control
- clock pressure
- move forcingness, such as check/capture/threat
- move type, such as quiet retreat, sacrifice, or long tactic
- whether it is an only move

Initial findability labels:

- `obvious`
- `findable`
- `hard`
- `very_hard`
- `engine_like`
- `unknown`

Findability should affect wording, not objective move quality.

Bad:

```text
You should obviously have played Qh5+.
```

Better:

```text
The hard move to find was Qh5+. The reason it matters is that it checks first,
so Black has to respond before improving the defense.
```

## Time Situation

Time changes practical expectations.

The context engine should model time situation when data is available:

- `unknown`
- `classical_or_no_pressure`
- `rapid_normal`
- `blitz_normal`
- `low_time`
- `time_scramble`

Use:

- time control
- clock before move
- increment
- move number

Time situation should not change the objective quality label. A blunder remains
a blunder. But it should affect coaching wording:

```text
In blitz this is understandable, because the best move is a forcing detail.
Objectively, though, the move gives Black time to stabilize.
```

If clock data is missing, use the time control only and mark confidence lower.

## Practicality Categories

For each important alternative, derive a practicality category:

- `clear_recommendation`: strong and findable
- `practical_try`: close to best and easier to find
- `hard_but_important`: difficult, but central to the position
- `engine_benchmark`: best by engine, but not useful as the main recommendation
- `only_move`: must be mentioned despite difficulty
- `unknown_practicality`: insufficient human/time evidence

This category should drive the explanation agenda.

## Minimal Evidence Packet

The evidence packet should be complete enough for verification.

KISS shape:

```json
{
  "context_version": "move_context.v1",
  "request": {
    "player_color": "white",
    "player_level": {"kind": "rating", "value": 1250, "system": "lichess"},
    "time_control": "blitz",
    "clock_before_seconds": 84.2,
    "played_move": "g2g4"
  },
  "position": {
    "fen_before": "...",
    "fen_after": "...",
    "side_to_move": "white",
    "move_number": 23,
    "phase": "middlegame"
  },
  "played": {
    "uci": "g2g4",
    "san": "g4",
    "legal": true
  },
  "quality": {
    "label": "mistake",
    "score_delta_cp_player_pov": -230,
    "wdl_delta_player_pov": {"win": -80, "draw": -360, "loss": 440},
    "severity_text": "the position changed from roughly equal to clearly better for Black"
  },
  "candidates": [
    {
      "san": "Qh5+",
      "uci": "d1h5",
      "role": "engine_best",
      "engine_rank": 1,
      "score_cp_player_pov": 62,
      "score_loss_vs_best_cp": 0,
      "pv_short_san": ["Qh5+", "Nf6", "Qxe5+"],
      "player_level_probability": 0.03,
      "time_adjusted_findability": "hard",
      "practicality": "hard_but_important",
      "recommendation_policy": "mention_with_caveat"
    }
  ],
  "main_point": {
    "concept": "forcing moves before quiet attacking moves",
    "claim": "g4 looked active, but Qh5+ was the forcing move that kept Black responding"
  },
  "allowed_claims": [
    "g4 was a mistake",
    "Qh5+ was the key alternative",
    "the issue was move order",
    "the better move was hard to find at this level"
  ]
}
```

This packet can be stored and used by the verifier. The LLM does not necessarily
need every field.

## Minimal LLM Context

The LLM context should be a compact projection from the evidence packet.

It should be generated by deterministic context-engine code, not by an LLM.

KISS shape:

```json
{
  "played": "g4",
  "quality": "mistake",
  "player_level": "1250",
  "time_situation": "blitz_normal",
  "severity": "from roughly equal to clearly better for Black",
  "main_point": "g4 looks active, but it spends a tempo before the forcing check.",
  "best_or_key_move": {
    "move": "Qh5+",
    "practicality": "hard_but_important",
    "findability": "hard",
    "reason": "it checks first and keeps Black responding"
  },
  "human_note": "At this level and time control, missing Qh5+ is understandable; the lesson is to check forcing moves before quiet attacking moves.",
  "allowed_claims": [
    "g4 was a mistake",
    "Qh5+ was the key forcing move",
    "the best move was hard to find",
    "Black gets time to stabilize after g4"
  ]
}
```

No tone, audience, or generic style fields are needed here. The static prompt
can say:

```text
Use the supplied context only. Return one concise explanation string.
```

## Explanation Agenda

The context engine should choose one agenda before generation.

Agenda fields:

- move quality
- main reason
- key alternative
- practicality caveat
- human note, if supported
- claims the LLM may make

The agenda is not prose polish. It is the chess teaching decision.

Example agendas:

```text
Objective mistake, best move findable:
  "Explain why the played move failed and recommend the better move directly."

Objective mistake, best move hard:
  "Explain the mistake and say the better move was a hard forcing resource."

Engine best is not meaningfully better:
  "Do not overemphasize the engine-best move; explain the general better idea."

Only move:
  "Mention the exact move even if hard, because it was necessary."
```

## Pitfalls The Context Must Prevent

### Recommending Impossible Moves Too Strongly

If a move has low human probability and low findability, the context should not
make it sound obvious.

Prevention:

- include findability
- include recommendation policy
- include human note

### Treating Maia As Quality

Maia probability means "likely for humans", not "good".

Prevention:

- keep objective `quality` separate from human `findability`
- do not derive move quality from Maia

### Ignoring Time Pressure

A low-time blunder can still be objectively bad, but the explanation should be
less accusatory and more practical.

Prevention:

- include time situation when available
- mark time confidence if only time control is known

### Overvaluing Engine Precision

If the top two engine moves differ by a tiny margin, the context should avoid
making the exact top move sound essential.

Prevention:

- include `score_loss_vs_best_cp`
- identify close practical alternatives
- explain ideas, not engine preference, when moves are close

### Unsupported Tactic Claims

A concept tag is not enough.

Prevention:

- include allowed claims
- include concept source/confidence in the evidence packet
- verify tactic words against allowed claims

### Wrong Perspective

Every human-facing score must be from the player whose move is being explained.

Prevention:

- store player color
- normalize score deltas to player point of view
- keep raw engine perspective out of LLM context unless needed for debugging

## Other Evidence Worth Considering

Do not add extra evidence sources unless they improve the one explanation
string. The useful candidates are:

### Syzygy Tablebases

Use for exact endgame truth when available. They are especially useful when
Stockfish gives heuristic-looking scores in tablebase positions.

### Lichess Empirical Frequencies

Use clean Lichess data to estimate how often candidate moves are actually played
by rating and time control. This helps calibrate practical recommendations.

### Lichess Puzzle Themes

Use later as concept-label support, not as a product feature. Puzzle themes can
help validate that a position is about a fork, pin, mate threat, and so on.

### Opening Frequency From Clean Data

Use cautiously. In opening positions, a common human move that is close in
engine score may be a better practical recommendation than a narrow engine
preference. Do not turn this API into repertoire advice.

Avoid adding another chess engine unless it supplies a distinct signal. For the
initial product, Stockfish plus human-likeness/practicality evidence is the
right balance.

## Context Versions

### v0: Objective Stockfish Context

Goal: explain one move correctly.

Includes:

- reconstruction
- Stockfish top candidates
- played-move forced analysis
- after-move reply
- score normalization
- quality label
- simple main point

No human findability claims unless backed by evidence.

### v1: Practical Candidate Context

Goal: stop over-recommending engine-only moves.

Adds:

- candidate roles
- score loss versus best
- recommendation policy
- practical alternative detection
- findability placeholder: `unknown` when Maia/frequency data is absent

### v2: Maia-Calibrated Context

Goal: explain whether key moves are common, hard, or hidden at the player's
level.

Adds:

- Maia probabilities for played and candidate moves
- rating-bucket comparison
- time-control model selection when available
- findability labels

### v3: Time-Calibrated Context

Goal: adjust wording for blitz, low time, and time scrambles.

Adds:

- clock-aware time situation
- confidence on time estimates
- time-adjusted findability

### v4: Empirical Frequency Context

Goal: improve practical recommendations with observed human play.

Adds:

- rating/time-control move frequencies from clean data
- sample counts
- confidence
- sparse-data safeguards

### v5: Evaluation-Calibrated Context

Goal: optimize fields based on measured explanation quality.

Adds:

- context ablation tests
- human coach comparison
- field usefulness scores
- regression sets for overclaiming, wrong perspective, and engine-only
  recommendations

## Iteration Method

For each context version:

1. Create frozen examples across rating, phase, time control, and move quality.
2. Build evidence packets.
3. Build LLM contexts.
4. Generate explanation strings.
5. Verify legal moves, claims, score perspective, and quality label.
6. Have human or rubric review judge coaching quality.
7. Record failures as regression cases.
8. Adjust context fields or selection heuristics.

Key eval questions:

- Did the context pick the right main point?
- Did it distinguish engine best from practical recommendation?
- Did it include findability when recommending a hard move?
- Did time situation affect wording without changing objective truth?
- Did the explanation mention only supported claims?
- Did it sound like a coach instead of Stockfish prose?

## Acceptance Criteria

The context engine is working when:

- ambiguous input fails clearly
- board reconstruction is deterministic
- played move legality is verified
- engine scores are normalized from player perspective
- mate scores remain separate from centipawns
- every recommended move has objective score evidence
- every recommended move has findability or `unknown`
- hard-to-find best moves are caveated
- close practical alternatives are recognized
- optional Maia/frequency evidence is never treated as objective quality
- the LLM context is compact enough to generate one explanation string
- the verifier can check the final explanation against the evidence packet

## Final Context Promise

For the requested move, the context engine should tell the LLM:

```text
Here is what was played.
Here is how good or bad it was.
Here is the key alternative.
Here is whether that alternative was realistic to find.
Here is the main chess reason.
Here is the caveat, if the best move is hard.
Here are the claims you may safely make.
Return one clear explanation string.
```

That is the context engine target.
